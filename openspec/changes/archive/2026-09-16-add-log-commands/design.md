## Context

`build/journal.md` lines and `request_log` entries are both currently authored inline
by whatever agent/orchestrator turn is writing them -- the phase docs describe the
target format and the orchestrator composes it by hand (a markdown line, or a JSON
object merged into `BUILD_PLAN.json`). Both scripts are stdlib-only, called via
`Bash` per the rest of `src/`.

## Goals / Non-Goals

**Goals:**
- One command per journal append; one command per request_log append.
- `ts` for a new `request_log` entry is generated by the command, not typed by the
  caller -- removes the one field most prone to drift (wrong format, stale value
  copied from a prior entry).
- Keep `request_log_search.py`'s existing `search` behavior and output byte-identical
  under its new subcommand name.

**Non-Goals:**
- No change to `build_plan_schema.json` -- `add` writes entries that already satisfy
  the existing schema.
- No locking/concurrency handling -- these scripts are called sequentially by a single
  orchestrator turn, same as every other `src/` script.
- No batch-append (multiple entries in one call) -- every call site appends exactly
  one entry/line at the point the fact is established.

## Decisions

**`journal.py append` and `request_log_search.py add` follow the shape `telemetry.py
append` already established** (`skill/phase3_build.md`'s Implementation audit calls
`telemetry.py append build/attempts.jsonl --field k=v ...` to append one record to
`build/attempts.jsonl`, invoked the same way generated part scripts are: `uv run
--project "$SKILL_DIR" python "$SKILL_DIR/src/<script>.py" ...`). This change extends
an existing convention -- a small stdlib `append` CLI per log file -- to the other two
logs the orchestrator writes by hand, rather than introducing a new pattern.

**`journal.py` is a new file, not folded into an existing script.** Nothing in `src/`
currently touches `build/journal.md`; there is no existing module to extend.

**`request_log_search.py` gains a subcommand rather than becoming a second file.**
The user's request named `request_log.py add` illustratively, but the read path
(`search_request_log`) and the write path both operate on the same
`BUILD_PLAN.json.request_log` array, and `request_log_search.py` already owns that
file. Splitting into `request_log_search.py` (read) + a new `request_log.py` (write)
would give the same array two entry points with no functional benefit. Restructuring
the existing CLI with `search`/`add` subparsers keeps one file, one array, one place
to update if the entry shape changes. `search_request_log()` (the importable function
`render_prompt.py` uses) is unchanged.

**`add` takes `--kind` and `--text` as required flags, `--level`/`--target` optional,
matching the existing `--level`/`--target` filter flags' vocabulary** (`--target` may
repeat; stored as the `targets` array). `--kind initial` is rejected by `add` --
`add` is for the append-only phase 1-4 path (`clarification`/`correction`); the
`initial` entry is written once by the planner when `BUILD_PLAN.json` is first
created, not appended later.

**`add` validates against `build_plan_schema.json` before writing** (reusing whatever
`plan_validate.py` already imports for schema loading) so a malformed `--level`/`--kind`
value fails at the CLI rather than silently corrupting the plan; exit code 1 with the
validation error on stderr, no write.

**`journal.py append` takes the milestone key and text as separate arguments**
(`append <path> <phase>/<milestone> <text>`), not one pre-formatted line, so the `-
` prefix and `: ` separator live in one place instead of being retyped at each call
site.

## Risks / Trade-offs

- [Subcommand restructuring breaks any external/undiscovered call site still invoking
  `request_log_search.py <plan> --query ...` without a subcommand] -> grep found all
  call sites are in this repo's own docs/tests, which this change updates in the same
  commit; no external consumers exist for a skill's internal tooling.
- [`add`'s schema validation reads `build_plan_schema.json` on every call] -> the file
  is small and already loaded by `plan_validate.py` on every gate run; no measurable
  cost.
